# VPN 开启后的应用联网与 debug 性能

## 原因与修复

公共代理服务默认关闭后，`external_http_route` 仍将应用内订阅请求发送到配置的
`127.0.0.1:7890`；IP 检测还以公共代理开关为前提，直接跳过检测。因此浏览器可以联网，
Paws 自己的更新和检测却失败。这是 Paws 接入层的问题，与 Meow 0.22.0 的配置解析无关。

VPN Extension 现在在受系统网络保护的进程内启动一个独立的应用 HTTP 代理，绑定
loopback 随机端口，使用每次连接新生成的 256 位凭据，并限制为 16 个连接。端点只随当前
owner 的私有共享内存状态同步，不进入 UI 快照或日志。公共代理和控制器开关保持原语义。
订阅与 IP 请求使用该端点；重新连接会更换端口和凭据。IP 请求失败时保留错误，避免回退
物理网络后误报出口地址。

规则模式自动组尚未取得首次测速结果时，Meow 会先使用列表首个节点；本次在零延迟的
启动验收中观察到连接重置，直连模式的首次请求则成功。应用 GET 请求针对连接重置采用
有上限的重试（最多 5 次，退避总计 5.5 秒，只在最初 10 秒允许开始重试），始终使用同一
代理通道。直连请求、HTTP 错误状态和配置错误不进行这种重试，最终失败继续记录详细错误。

订阅请求失败现在直接记录操作名、路由、耗时及底层错误链，无须依赖 tracing subscriber。
URL、订阅路径中的凭据和内部代理密码会打码。日志页面合并本进程、引擎和 Extension
日志时按时间保留最新 256 条，防止旧 VPN 日志挤掉刚产生的应用错误。落盘仍遵循用户的
日志记录开关。UI 共享内存初始化不再清除日志开关或早期错误，保留用户选择；全新安装仍
默认关闭日志记录。此前冷启动重置开关，导致用户重开应用后无法捕获启动错误。

无效配置验收还发现，VPN 事务开始前的校验失败仅进入系统日志。现在统一的 Meow 配置
加载入口也直接捕获错误，记录版本、耗时和打码后的完整原因，不再依赖后续 reload/start
错误处理。测试覆盖无效 UUID 在事务开始前被拒绝、凭据打码及应用日志文件落盘。

VPN 通知原来每秒读取完整 `querySnapshot()`，连同数千条规则一起克隆、序列化和跨 NAPI
传输。现在 `queryTrafficSpeed()` 只读取上传、下载两个数值。debug native 保留断言和调试
符号，应用代码使用 `opt-level=1`，第三方依赖使用 `opt-level=3`，避免代理与 TLS 在 `-O0`
下运行。启动日志分别记录创建 TUN、网络保护、配置加载和 native 启动耗时。

日志 subscriber 也遵循运行配置固定的 `log-level=info`，在格式化事件字段前过滤
debug/trace。之前会记录大量 TLS 跟踪，导致额外 CPU 开销并挤占错误列表；相关测试确保
verbose 字段不会被格式化，同时 error 仍被捕获。

冷启动 debug 自动连接还修复了另一个时序问题：等待 VPN 插件安装、建立旧 owner 清理
屏障后才发起连接，避免工厂创建后立即启动被安装阶段的新 intent 取消。

优化构建暴露的配置资源 ID 碰撞也已修复：同一时钟刻度下的连续导入使用进程内递增序号，
避免后一项覆盖前一项。

## 模拟器与隐私

参考 [h-openconnect 的模拟器 VPN 文档](https://github.com/harmony-contrib/h-openconnect/blob/main/docs/harmonyos-emulator-vpn.md)
及 [Paws 授权预置流程](harmony-emulator-vpn.md)，本次创建独立的手机模拟器，使用
HarmonyOS 7.0.0 / API 26。性能对照在 `Paws VPN Regression` 完成，最终功能验收在
`Paws VPN IPv4 Acceptance` 完成。SDK 镜像未修改；首次授权仅在停止的实例 overlay 中
预置，保留经过校验的原始备份。SDK inventory 尾随诊断输出的 JSON 解析已修正。

原实例两次出现整个 guest 无响应，SDK 内核日志包含系统 CPU 采集路径的告警。该实例
已停止并移除，修改后的 userdata 备份及 SDK 日志保留在本机私有目录；不能将这一现象
归因于 Paws。验收期间暂停了 IDE 的后台 Rust 检查，结束后恢复。

用户授权的真实订阅仅保存在本机私有目录与测试实例。验收使用 71 个节点、9 个组、9263
条规则，不将订阅 URL、节点、出口 IP、原始日志或界面截图提交进仓库。

`pawsVerifyAppHttp` 是 debug Want 验收入口，release 的应用 debug gate 与 native debug
assertions 双重阻止执行。它在真正的应用 UID 内更新当前订阅、检查出口 IP，并制造一个
无凭据的失败请求，检查错误是否出现在页面快照中且已打码。返回值只有耗时、布尔结果和
规则数量。它会启用该测试实例的日志记录。

## 实测记录

基线包能创建真实 `vpn-tun`，但应用内订阅更新失败，公共代理默认关闭时 IP 检测被跳过。
修复包在公共代理保持关闭的情况下完成真实订阅更新和 IP 检测。

最终包在规则模式冷启动后，首次订阅更新为 2399 ms，IP 检测和打码错误记录均通过。
其中一次连接重置被同一代理通道内的重试恢复。随后以无效 UUID 配置启动，配置正确被
拒绝，错误写入应用日志，凭据未出现在诊断中，失败后没有残留 TUN。还原真实订阅配置
后再次启动，订阅更新为 2593 ms，IP 检测和错误记录再次通过。

第三方测试应用只持有普通 INTERNET / GET_NETWORK_INFO 权限。系统 HTTP 的 IPv4
订阅请求在 VPN 开关前后均成功；但外部 TCP 的 TUN 计数和 native 接收日志不足以证明
它经过 TUN，显式绑定 SDK 的 VPN NetHandle 也未补足这一证据。访问 TUN 内部地址
可以触发 TCP 接收，但不代表外部 TCP 转发成功。因此未将浏览器联网成功、root shell
请求成功或 DNS 计数变化当成完整 TCP 路由验收。应用内订阅和 IP 验收则明确使用上述
受保护进程内的私有代理，已经通过。完整外部 TCP 路由仍需在实际设备补验。

debug 包仅在每次 netstack 启动后记录第一条 TCP 接收标记，避免诊断标记随连接量持续
产生额外日志；release 不记录该标记。

相同模拟器、已允许通知、前台静置 20 秒的软件 task-clock 采样：第一轮优化后 VPN 为
0.934 秒、UI 为 2.247 秒；加入 info 日志过滤后的 VPN 为 0.177 秒、UI 为 0.514 秒。
基线分别为 3.072 秒、1.974 秒，累计计数下降约 94% 和 74%。
采样为单次结果，修复包已开启错误日志，不能据此推算真机温度或续航。

基线启动观测为 3739 ms；修复过程中的正常启动观测为 804–1084 ms。模拟器被宿主构建
挤压时也观测到约 2.6 秒启动，不将不同负载下的单次值作为确定的性能上限。

原先偶发的 `meow-config` 报错尚无原始错误文本，不能断言与本次 HTTP 问题同源。
Meow 0.22.0 的配置校验、错误链与阶段诊断见当前实现；实际失败需以新增诊断继续归因。

同一签名 debug 包已覆盖安装到当前在线的 ALN-AL00。此前报告性能问题的 ALN-AL10
在最终安装时离线，因此该设备的温度、续航及状态同步延迟不计入已完成的验收。

## 本地检查

全 workspace 测试通过 446 项，平台测试通过 39 项。受本机磁盘空间限制，Rust 测试保持
优化等级与断言，关闭测试产物的 debug 信息和 incremental 缓存：

```sh
CARGO_INCREMENTAL=0 CARGO_BUILD_JOBS=4 cargo test --workspace \
  --config profile.test.debug=0 --config 'profile.test.split-debuginfo="off"'
node --test scripts/test-vpn-platform.mjs
cargo fmt --all -- --check
```

普通 library clippy 检查完成。`clippy -- -D warnings` 被已有的手写 Default 实现等风格
警告阻断；本次新增的冗余字符串拷贝已修正。测试包仍保留 native debug 信息与 debug
assertions，测试环境的产物压缩选项不用于打包。
